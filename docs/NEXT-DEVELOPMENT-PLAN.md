# CherryPulse-KR-01 남은 개발 작업 계획

- 작성일: 2026-09-24
- 기준: `main`의 `f41cd5e` (2026-09-16), 저장소 문서와 코드 확인
- 용도: 후속 개발의 작업 목록·순서·완료 기준. 이 문서 자체는 구현 완료나 실제 주문 허가가 아니다.

## 1. 목표와 현재 기준선

사용자가 외부에서 찾은 종목을 등록하고 매수·매도 패턴을 연결한다. Windows 엔진은 수락한 설정에 따라 감시·주문·체결·보유 보호를 처리하고, 웹 보드는 적용 상태와 근거를 표시한다. 새 시스템은 종목 발굴, 전략 점수, 백테스트 승인 기능을 포함하지 않는다.

현재 `execution/`에는 SQLite 원장, 가상 dispatcher, 요청 중복 방지, 예약, 부분체결, 취소 `UNKNOWN`, 재시작 차단, 계좌 잠금, 격리 및 대조 근거 검사가 있다. 마지막 기록은 98개 pytest 통과다. 이는 2026-09-16 기록이며 이 문서를 작성하면서 Windows 검사를 재실행한 결과는 아니다. `back/legacy-2026-09-13/`은 참고용 보관본으로 활성 코드에서 import하지 않는다.

미구현: 실제 키움 어댑터, 시세 연결, 설정 및 패턴 평가기, 손절 자동 실행, 매수 자동 실행, 웹 보드, 클라우드 동기화, 배포. 기존 가상 청산 의무의 매도 제출은 **손절 조건 평가가 구현되었다는 뜻이 아니다**. 현재 `Scope.broker_adapter`는 `virtual`만 허용한다.

우선 기준은 [개발방향](CherryPulse-KR-01-Development-Direction.md), [개편 계획](CherryPulse-KR-01-Rebuild-Plan.md), [실행 계약](REBUILD-02-CONTRACTS.md), [검증 매트릭스](REBUILD-02-TEST-MATRIX.md), [미확인 사항](REBUILD-02-OPEN-QUESTIONS.md) 순서다. 이 계획과 충돌하면 해당 기준 문서를 먼저 대조하고 결정을 기록한다.

## 2. 작업 공통 규칙

각 작업은 기존 코드·계약 확인 → 누락된 결정 기록 → 최소 구현 → 관련 단위/SQLite 연동/가상 시나리오 검사 → 결과 문서 갱신 순서로 수행한다. 수정 전 `git status`로 로컬 변경을 보존한다. 변경 파일, 판단 근거, 실행 명령, 실제 결과, 미검증 범위를 작업 결과에 남긴다. 검사 개수만으로 계좌 연동이나 운영 준비를 완료 처리하지 않는다.

모든 주문 기능은 요청 전송 상태와 주문 생명주기를 분리하고, `Q0 + D = F + C + A`를 논리 주문 단위로 보존한다. 확인 전 예약을 해제하지 않는다. 전송/취소가 불명확한 `UNKNOWN`에서 자동 재전송하지 않는다. 신규 매수 제한과 보유 청산 의무를 분리한다. 보호 청산은 미확인 수량을 중복 제출하지 않고, 미해결 상태를 노출한다. 시세 수신 실패 또는 PC 종료 시 청산이 보장된다고 표시하지 않는다.

실제 주문 API, 모의계좌 주문 API, 운영 DB 변경, 배포는 각 단계의 별도 명시적 지시 및 환경 확인 이후에만 실행한다. 문서와 가상 구현은 해당 작업을 수행하지 않는다. 커밋·푸시는 저장소 `AGENTS.md`에 따라 별도 요청을 받아 수행한다.

### D01 — 먼저 확정할 데이터와 권한 계약

- 종목별 하나의 활성 설정, 패턴 ID/불변 버전, 적용 범위(신규 매수와 기존 보유 보호), 생성·수락·거절·중지 시각을 정의한다.
- 명령의 주체, 계좌/환경 범위, 권한, 명령 ID·멱등 키, 기대 설정 버전, 만료 시각과 감사 근거를 정의한다. 웹에서 저장한 값은 엔진이 인증·검증·수락하기 전까지 미적용이다.
- 보호 규칙 교체 중 보유 수량에 적용되는 이전/새 버전과 실패 시 유지할 규칙을 정의한다. 보유·미체결이 있을 때 패턴 삭제로 보호를 없애지 않는다.
- 최초 손절 후보는 **고정 가격 이하**와 **확인된 평균 매수가 대비 하락률**이다. 수치, 기준 가격의 출처, 틱 시각과 신선도, 발동 비교(`<=` 등), 유효 세션, 주문 유형·호가, 재발동·재진입 정책은 사용자 결정 전 임의 기본값을 확정하지 않는다. 범위가 확정되지 않은 경우 스키마와 비활성 예시만 만든다.
- 설정 명령과 매매 주문 명령을 구별한다. 클라우드가 직접 브로커 주문 생명주기를 확정하지 않으며, 브로커 확인 이벤트와 원장을 기준으로 상태를 바꾼다.

### D03~D04 — 손절의 필수 가상 시나리오

1. 최초 매수 부분체결 직후 해당 체결 수량에 보호 규칙이 붙는다. 평균 매수가 변경과 추가 체결은 버전 및 기준값 정책에 따라 재계산한다.
2. 같은 시세·중복 시세·중복 신호를 재처리해도 같은 청산 의무와 수량을 중복 예약·제출하지 않는다.
3. 기존 매도 예약과 매수 잔여 주문을 대조하고, 취소 요청 접수만으로 매수 잔여분을 확정 취소하지 않는다. 취소 중 추가 체결이 오면 새 보호 수량을 반영한다.
4. 부분 매도 후 남은 관리 수량은 보호한다. 매도 접수·체결·거절·취소 `UNKNOWN` 각각의 예약과 가능한 다음 행동을 검사한다.
5. 재시작 직후 미확정 요청·주문·잔고를 대조할 때까지 새 중복 매도를 차단한다. 불일치와 연결 불명 이벤트는 원문을 보존하고 격리한다.
6. 거래 시간 종료, 신규 매수 중지, 웹 단절, 오래된 시세를 각각 검사한다. 브로커 허용 시간 밖의 실행은 임의로 성공 처리하지 않고 보호 미완료 사유를 남긴다.

### D06~D07 — 실증 전에 남는 차단 사항

[Q01~Q13](REBUILD-02-OPEN-QUESTIONS.md)을 상태별로 갱신한다. 특히 주문번호 유일성·정정 연결(Q01), 체결 고유키와 중복(Q02), 정정 수량(Q03), 취소 완료와 지연 체결(Q04), 전송 실패의 미호출 증거(Q05), 매도 가능 수량(Q06), 조회 페이지 완전성(Q07), 역순 체결(Q08), 지정 PC 잠금(Q09), 호가·시간·설치 버전(Q10), 기존 보유 인계(Q11)가 주문 활성화의 근거다. 증거를 얻지 못한 부분은 추정으로 메우지 않고 어댑터에서 차단하거나 `UNKNOWN`·격리로 남긴다. 실제 계좌로 수집할 자료와 호출 범위는 별도 작업에서 명시한다.

### D08~D10 — 연결과 운영

- 클라우드 DB에는 원하는 설정과 표시용 복제 상태를 보관하고, Windows 로컬 원장을 주문·체결·예약의 실행 기준으로 둔다. 업로드 재시도는 이벤트 ID로 멱등 처리하고 원장 순서를 보존한다.
- 웹은 엔진 접속 상태, 마지막 시세와 동기화 시각, 설정 적용 버전, 청산 진행과 차단 사유를 표시한다. 새로고침·카드 이동은 주문이나 체결을 만들지 않는다.
- 운영 인수 시 기존 수동 보유, 미체결, 다른 PC의 실행 가능성, 잠금 경로, 운영 DB 이전을 조사한다. 과거 가상 DB의 조회 근거 없는 `RECONCILED` 기록은 자동으로 정상 근거로 승격하지 않는다.
- `back/` 삭제는 재사용·복구 필요성 및 데이터 보존 확인 후 별도 요청으로만 검토한다.

## 4. 작업 착수 및 종료 기록 형식

각 ID를 시작할 때 결과 문서에 다음을 기록한다.

```text
작업 ID / 기준 커밋 / 작업 브랜치와 기존 로컬 변경
읽은 기준 문서 / 확정된 결정 / 미결정과 차단 정책
변경 파일 / 사용자에게 보이는 동작
검사 명령과 종료 코드 / 통과한 구체 시나리오 / 미실행 검사와 이유
실제 키움 API 호출 여부 / 운영 DB 변경 여부 / 배포 여부
남은 위험 / 다음 작업의 입력
```

Windows 개발 환경은 [개발 환경 문서](DEVELOPMENT-ENVIRONMENT.md)를 따른다. `.venv`의 Python 3.10 **32비트**와 고정 의존성을 사용하고, 원장 검사는 고유 `--basetemp` 경로로 실행한다. 최소 검사에는 관련 pytest, 전체 pytest, Ruff, basedpyright, 가상 데모가 포함된다. 웹 작업에는 빌드와 모바일 화면 확인을 추가한다. 키움 어댑터 단계에서는 가상 재생 검사와 실제 근거 검증 결과를 별도로 보고한다.

## 5. 첫 구현 작업의 종료선

**기준 문서 작성 시 계획된 첫 작업은 D01이었다.** 현재 D01의 원하는 설정 수신·보관 모델과 D03의 가상 손절 기능은 부분 구현되어 있으나 인증된 적용 경계와 계획상 완료 조건은 충족하지 않았다. 현재 D02 보드는 종목 및 손절 패턴의 브라우저 로컬 초안으로 부분 구현되어 있다. 2026-09-25 기준 진행과 검사 결과는 [작업 이어가기 기록](WORK-CONTINUATION-STATUS.md), [D02 기록](D02-BOARD-PROGRESS.md), [D03 기록](D03-VIRTUAL-STOP-PROGRESS.md)을 따른다. 인증·설정 적용 원자성, 시세/세션 및 키움 실증에 막히지 않는 비활성 보드 작업은 계약을 지키는 범위에서 진행할 수 있다. 어떤 로컬 초안도 감시를 활성화하거나 엔진 적용 상태로 표시하지 않는다.
