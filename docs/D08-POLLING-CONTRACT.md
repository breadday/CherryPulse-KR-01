## 책임 분리

- 클라우드(Supabase): 원하는 설정(desired), 명령 전달, 표시용 복제 상태.
- Windows 로컬 SQLite: 적용 설정·요청·주문·체결·예약 원장. 주문·체결·예약의
  실행 기준은 로컬 원장이며 클라우드가 브로커 주문 생명주기를 확정하지 않는다.
- 엔진 수락 응답 없이 웹을 `감시 중`으로 표시하지 않는다.

## 폴링 방향 두 가지

1. 하향(명령): 엔진이 주기적으로 미적용 명령을 조회한다. 스코프는
   (account_id, environment)이며 서버 순번 오름차순으로 읽는다.
2. 상향(이벤트): 로컬 outbox의 미업로드 이벤트를 순서대로 업로드한다.
   이벤트 ID로 멱등 처리하고 원장 순서를 보존한다.

## 명령 적용 규칙 (기존 D01 재사용)

- 수신한 명령은 기존 `ConfigInbox.receive` → `resume_pending()` → 원장 적용
  프로토콜로만 적용한다. 동기화 계층은 독자 적용 경로를 만들지 않는다.
- 동일 명령 ID 재수신은 기존 결정을 반환하고, ID 내용 충돌·버전 충돌·만료는
  거절한다. 역순 도착 명령은 기대 버전 검사에서 거절되며 조용히 적용하지
  않는다.
- `APPLIED`는 로컬 기록 완료이며 감시 활성화가 아니다.
- 오프라인 기간의 명령은 복구 후 폴링에서 순서대로 수신하고, 만료된 명령은
  적용하지 않고 만료 사유를 남긴다.

## 업로드 규칙

- 업로드 단위는 원장 이벤트이며 재전송해도 서버에서 이벤트 ID 중복으로
  합쳐진다. 같은 이벤트의 중복 업로드는 정상 동작이다.
- 업로드 성공 표시는 서버의 수신 확인 뒤에만 로컬 outbox에 기록한다.
  확인 없는 전송을 성공으로 표시하지 않는다.

## 실패·차단 정책

- 폴링 실패·인증 실패·서버 오류 시 로컬 원장·감시 상태를 바꾸지 않고
  마지막 성공 동기화 시각과 실패 사유만 남긴다.
- 인증 토큰·키 등 비밀값은 저장소·문서에 기록하지 않는다.
- 전송/적용 불명확 상태에서는 자동 재전송·재적용하지 않고 `UNKNOWN`·격리로
  남긴다.
