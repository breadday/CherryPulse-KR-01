## 1. 하나의 개발 기준

사용자 종목 등록 → 매수/매도 패턴 연결 → 감시 시작 요청 → 엔진 수락 → 조건 감지 → 주문·체결 추적 → 보유 보호 → 청산의 흐름만 개발한다. 기존 종목 선정·추천·성과 평가·후보 승인 방식은 새 제품에서 제거한다.

기존 방식의 실행 파일과 안내는 back/으로 이동했다. 새 프로젝트에 구·신 실행 경로를 병행하지 않는다. 필요한 키움 통신·주문·체결 계산만 계약에 맞게 검토하여 새 모듈로 편입한다. 보관본을 런타임 의존성으로 삼지 않는다.

## 2. 목표 구조

| 구성 | 책임 |
|---|---|
| Vercel 웹/API | 로그인, 보드, 종목·매수/매도 패턴 관리, 설정 요청, 상태·기록 조회 |
| 관리형 DB | 원하는 설정, 명령 전달·수락 결과, 웹 조회용 실행 상태 |
| Windows 엔진 | 실제 시세, 패턴 판단, 단일 주문 제출, 보호 청산, 재시작 대조 |
| 로컬 SQLite | 적용 설정, 요청·주문·체결·예약·배정 원장, 업로드 대기 이벤트 |

웹 접속 여부와 무관하게 적용된 보호 규칙은 로컬에서 수행한다. 시세·증권사 연결이 끊기면 마지막 수신과 실행 불가를 표시한다. 보드는 엔진 상태의 표시이며 카드 드래그로 주문 상태를 바꾸지 않는다.

예정 경로는 `web/`, `contracts/`, `execution/`, `patterns/`, `adapters/`, `persistence/`, `sync/`, `tests/`다. 현재 execution/과 tests/를 구현했으며 나머지는 후속 단계다. `runtime/`은 기존 .gitignore에서 실행 산출물로 제외하므로 소스 경로로 사용하지 않는다.

웹 프레임워크·DB 공급자·패키지 버전은 기반 구축 시 공식 문서와 계정 환경을 확인해 고정한다. 키움 호환 Python/Qt 환경을 확인하기 전에 언어 버전을 올리지 않는다.

## 4. 패턴과 화면의 범위

패턴은 버전이 있는 조건과 주문 행동이다. 최초 후보는 가격 기준 매수, 가격 기준 손절, 평균 체결가 대비 비율 손절이다. 실제 수치·시간 단위·주문 방식·재발동·재진입·취소 한도는 상세 명세에서 정한다. 임의 코드 실행 기능은 만들지 않는다.

화면은 등록·설정 / 매수 감시 / 매수 주문 중 / 보유·매도 감시 / 매도 주문 중 / 종료의 보드와 종목·패턴·주문 기록·운영 상태 메뉴로 구성한다. 매수 부분체결 단계에서도 보유량과 보호 상태를 보여준다. 등록만으로 주문하지 않으며 반영 대기와 감시 중을 구별한다.

## 5. 개발·검증 방식

작업마다 계약 → 최소 구현 → 단위·DB 연동 검사 → 실제 화면/가상 어댑터 시나리오 확인 → 결과 기록 순서로 진행한다. 전략 수익률·백테스트 점수로 기능 승격을 판단하지 않는다. 체결 중복, 취소 UNKNOWN, 추가 체결, 잔고 불일치, 재시작, 잠금 실패가 핵심이다.

소프트웨어 검증과 실제 계좌 검증은 구분한다. 문서 기대값 검산만으로 엔진 통과를 주장하지 않는다. 계좌 실주문·배포는 별도 명시적 요청에 따라 진행한다.

## 6. 인계·보관 원칙

파일 이동은 계좌 포지션을 청산하거나 실행 중 프로세스를 종료하지 않는다. 현재 .env, 일봉/샘플 데이터, 기존 백업과 운영 기록은 보존한다. 새 엔진 도입 전 보유·미체결·외부 수동 보유를 대조하고 관리 배정을 명시한다.

구 안내는 활성 문서에서 제거했다. [보관 목록과 복구 방법](REBUILD-01-ARCHIVE.md)을 개발 참고로 사용하고, back/의 구 AGENTS·계획·전략 설명을 새 지시로 따르지 않는다.
