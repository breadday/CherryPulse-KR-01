# REBUILD-04 요청 실패와 계좌 잠금

2026-09-15. [개발방향](CherryPulse-KR-01-Development-Direction.md)과 [실행 계약](REBUILD-02-CONTRACTS.md)에 따른 내부 실행 기반의 두 번째 구현 기록이다. 이전 [SQLite 원장 기록](REBUILD-04-LOCAL-LEDGER.md)의 후속이며, 실제 증권사 연동이나 REBUILD-04 전체 완료를 뜻하지 않는다.

## 구현한 동작

- `SEND_FAILED`는 미호출 또는 검증된 미전송 증거가 있을 때만 신규 주문 예약을 해제한다. UNKNOWN에 단순 미호출 주장을 붙일 수 없고, 접수·체결 증거가 있으면 미전송 증명을 거절한다.
- 신규 요청의 증권사 거절은 REJECTED로 기록한다. 미전송·거절로 주문이 성립하지 않은 경우 체결량과 취소량을 만들어 내지 않는다. 활성량·예약은 0이며 수량 항등식 차이는 적용 불가인 `None`이다.
- 취소·정정 요청의 전송 거절 또는 효과 거절은 원주문의 예약과 수량을 해제하지 않는다. 거절된 변경 요청은 종료되어 별도 키의 변경 의도를 받을 수 있다.
- 거절 뒤 지연 체결처럼 모순된 증거도 원장에 남긴다. 실제 체결은 관리량에 반영하고 남은 노출을 예약하며 대조 대상으로 유지한다. 재시작 복구도 이를 포함하고 자동 재전송하지 않는다.
- 청산 중 매도 실패·거절 이후 자동 재주문은 하지 않는다. 재시도 정책은 후속 개발 대상이다.

## 계좌 소유와 시작 조건

`execution/ownership.py`가 Windows 파일 잠금을 먼저 획득하고, 그 소유 객체를 `Ledger(path, lease)`에 전달한다. 잠금 키는 어댑터·계좌 내부 ID·환경으로 구성하며 execution UUID를 제외한다. 같은 계좌의 다른 실행 UUID도 경합한다. 가상 PAPER와 LIVE 범위는 분리된다.

잠금 실패 시 원장 연결 전에 거절한다. 종료된 소유 객체나 직접 생성한 미소유 객체로 쓰거나 전송할 수 없다. 한 소유 세션은 한 DB 경로에만 연결할 수 있다. 전송 전체를 소유 구간으로 감싸 호출 중 잠금 해제가 끼어들지 않도록 한다.

매번 잠금을 새로 획득하면 전송 재개는 닫힌 상태다. `approve_virtual_reconciliation(expected_revision)`은 원장 변경 번호가 일치하고 미확정 요청·수량 불일치가 없을 때 가상 세션을 연다. 증거 수집은 닫힌 세션에서도 가능하지만 신규 명령과 전송은 차단한다. 이 메서드는 내부 가상 검증용이며 사용자 인증이나 증권사 잔고 대조를 대신하지 않는다.

현재 잠금 디렉터리는 호출자가 지정한다. 실제 운영 전에는 같은 계좌가 반드시 같은 지정 디렉터리를 사용하도록 고정하고 Windows 사용자 간 ACL·세션 범위를 검증해야 한다. 다른 PC를 막는 기능은 없다. 파일은 잠금 해제 시 삭제하지 않는다. 구현 근거: [Python 3.10 msvcrt.locking](https://docs.python.org/3.10/library/msvcrt.html#msvcrt.locking).

## 검증 결과

- 전체 pytest **59개 통과, 76.96초**. 기존 40개 검사에 요청 결과·계좌 소유·시작 게이트·별도 프로세스 검사를 추가했다.
- 실제 별도 Windows 프로세스가 잠금을 보유할 때 경쟁 프로세스는 진입하지 못하고 SQLite 파일 해시가 유지됨을 확인했다. 보유 프로세스의 `os._exit(23)` 이후 재획득과 미확정 요청의 대조 전 전송 차단을 확인했다.
- Ruff ALL·포맷 24개 파일 통과. basedpyright 오류 0·경고 0. Python 코드 규칙 24개 파일 위반 0.
- 모듈 데모를 직접 실행해 관리량 70, 예약 0, 취소 UNKNOWN 예약 100, 취소 확인 뒤 예약 30, 가상 호출 2회, 재생 변경 0을 확인했다.
- 일부 도구 호출이 테스트 완료 전에 시간 초과를 반환했다. 같은 실행의 최종 로그에서 59개 통과를 확인했다. 실행 지연 원인은 확정하지 않았으며 성능 검증 완료로 해석하지 않는다.

검사 파일은 `test_request_outcomes.py`, `test_account_lock.py`, `test_session_gate.py`, `test_lock_process.py`에 있다. 테스트는 임시 DB와 가상 계좌 식별자만 사용한다. 증권사 로그인·주문·배포는 실행하지 않았다.

2. 명령 인증·권한·만료·기대 버전, 전송 직전 실행 조건을 검증한다.
3. 매수·손절 패턴의 실제 조건, 설정 버전 적용, 청산 완료·재개 이력과 외부 보유 인계를 구현한다.
4. 키움 반환값별 미전송 근거와 고유 체결 식별을 확인하고, 지정 PC·공유 잠금 경로·ACL을 검증한 뒤 별도 허가된 계좌 연동을 수행한다.

`NOT_INVOKED`와 `VERIFIED_UNSENT`는 신뢰된 가상 어댑터 증거다. 키움 오류를 이 분류로 매핑하는 작업은 미완료이며 timeout·예외만으로 안전한 재주문을 허용하지 않는다. 기존 종목 발굴·추천 방식은 복원하지 않았고 `back/`의 코드를 실행하거나 import하지 않았다.

## 후속 구현: 전송 직전 조건 확인 — 2026-09-15

가상 dispatcher가 SENDING을 기록하는 동일 트랜잭션에서 최신 원장을 다시 확인한다. 신규 매수 의도 저장 후 매수 중지·수량 불일치가 기록되면 전송하지 않는다. 원장의 체결 증거가 전송 기록보다 먼저 도착한 경우에도 같은 요청을 재전송하지 않는다. 이러한 요청은 재시작 시 RECONCILING으로 분류한다.

매수 중지만으로 신규 매도를 차단하지 않는다. 기존 취소·정정 전송 경로도 이 매수 제한에 포함하지 않는다. 중지로 보류한 요청에는 전송 또는 실패 사실을 임의로 추가하지 않으며 예약도 임의 해제하지 않는다. 현재는 원장 의도가 남으므로 중지 해제 후 다시 전송을 요청할 수 있다. 명령 만료·설정 기대 버전·재개 승인 정책은 별도 후속 작업이며 이 구현으로 완성된 것은 아니다.

`tests/test_dispatch_preflight.py`에서 5개 실패와 1개 정상 매도 검사를 먼저 관측하고 수정했다. 최종 전체 **65개 통과, 7.42초**. Ruff ALL·basedpyright 오류/경고 0·포맷 및 코드 규칙 25개 파일 통과. 직접 실행한 모듈 데모는 관리량 70·예약 0·가상 호출 2·재생 변경 0으로 기존 결과를 유지했다. 이전 76.96초 실행 지연의 원인이 해소됐다고 단정하지 않는다. 증권사 확인과 배포는 수행하지 않았다.

위 후속 작업 중 로컬 명령 만료·적용 버전 비교는 [명령 유효성 구현 기록](REBUILD-04-COMMAND-FRESHNESS.md)에서 구현했다. 현재 검사 수와 제한은 해당 기록을 따른다.
