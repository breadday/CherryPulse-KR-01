# REBUILD-02 API 근거 확인

2026-09-14. 국내 주식 OpenAPI+의 공식 문서와 로컬 설치를 대조했다. 서버 접속·주문·취소·조회 요청은 실행하지 않았다.

## 공식 근거

출처: 키움 [OpenAPI+ 개발가이드 v1.7](https://download.kiwoom.com/web/openapi/kiwoom_openapi_plus_devguide_ver_1.7.pdf). 53쪽 문서의 표시 쪽수 기준이다. 설치 OCX와의 실제 호환·필드 의미는 별도 검증한다.

| 위치 | 확인 사실 | 계약에 반영할 범위 |
|---|---|---|
| 16쪽 SendOrder | 주문 종류와 원주문번호 인자를 제공 | 내부 요청 종류와 대상 주문을 구분하되 정정 체인의 효과는 별도 검증 |
| 28쪽 OnReceiveChejanData | 주문체결 통보와 국내주식 잔고 통보를 구분 | 체결과 잔고 이벤트를 별도 원문으로 보존 |
| 30쪽 오류표 | -202는 전문 입력 오류, -307은 주문전송 실패, -308/-311은 주문전송 과부하로 기재 | 오류값 보존. 자동 재전송 가능 여부·미전송 증거는 별도 판정 |
| 42~43쪽 FID | 주문·체결번호 및 수량·잔고 관련 필드 존재 | 필드 존재와 유일성·누적량·예약 반영 시점을 구분 |

위 사실만으로 주문번호 유일성, 특정 시간 내 접수, 체결 순서, 정확한 정정/취소 수량 의미, 조회 스냅샷 동시성을 확정하지 않는다. REST나 해외파생 OpenAPI-W 규칙으로 보충하지 않는다.

## 설치 및 구 코드와의 차이

[환경 확인](REBUILD-01-ENVIRONMENT.md)에서32비트 OCX와 로컬 TR 자료의 존재를 확인했다. 현재 보관 어댑터는 체결 통보에서 FID909를 읽지 않고, 구 engine의 _normalize_fill_qty는 주문량에서 잔량을 빼 체결 증가량을 추론한다. 새 계약은 확인된 체결 고유키와 취소/정정 효과를 분리하므로 이 계산을 그대로 재사용하지 않는다.

구 _send_order_with_retry의 -202/-308 처리도 신규 요청 상태 계약에 맞게 다시 분류해야 한다. 오류 이름만 보고 네트워크 전달 여부를 확정하거나 UNKNOWN을 재전송하는 방식은 채택하지 않는다.

## 미확인 항목별 진척

| 항목 | 이번에 확인한 부분 | 남은 부분 |
|---|---|---|
| Q01~Q04 | 관련 필드·입력 및 설치 존재 | 번호 유일성, 정정 체인·취소 수량·지연 체결의 실제 매핑 |
| Q05 | 오류표 근거와 구 재시도 경로 | 명확한 미전송 판정과 오류별 재시도 정책 검증 |
| Q06~Q08 | 이벤트 종류와 로컬 조회 자료 존재 | 예약 반영·조회 완전성·요청/체결 상관관계 |
| Q09 | 현재 관련 프로세스·예약 작업 조사 | 단일 실행 잠금의 구현·충돌/종료 시험 |
| Q10 | 32비트 OCX·Python 후보·Qt 파일 존재 | 패키지 import·COM 호환·호가/시간/주문 방식 명세 |
| Q11 | 운영 DB 존재 | 계좌 잔고·미체결·관리 배정 |
| Q12 | 기존 계약 유지 | 첫 패턴 상세 규칙 |
| Q13 | 구 실행 경로와 환경 부분 조사 | 전 호출 그래프·간접 외부 실행·실제 인계 |

어느 항목도 전체 해소로 표시하지 않는다. 내부 원장·가상 어댑터·화면 개발에 필요한 계약은 계속 사용할 수 있으나 실제 주문 활성화의 근거로 삼지 않는다.
